# Contributing

Welcome. The most useful contributions:

1. **A new robotics PDE/ODE domain** — a class in `mw_framework/domains/` (or a JSON config — see `mw_framework/config.py` for the schema), plus a generator in `datasets.py` and an example. Every law needs a one-line `why`.
2. **Reproductions on real data** — open an issue with your setup and numbers, good or bad.
3. **Honest failures** — a case where MW loses to a baseline teaches more than one where it wins. Add it to `docs/LIMITATIONS.md`.

Before a pull request:

```bash
pytest -q
./run_all_examples.sh --quick
```

Style: short functions, docstrings that say *why*, physical units in names (`temp_c`, `r_int_mohm`).

# Limitations — read before deploying

Scope, inherited from the general [MW Framework](https://github.com/RahulModak74/MW_Geometric_Intelligence)
this repo is trimmed from. Each point was observed while building that repo's seven examples;
the numbered examples referenced below (00, 01, 05, 06) live there, not in this trim — this
repo's own result, with its own mixed findings, is in [ROBOTICS.md](../ROBOTICS.md).

**1. Physics does not always beat a plain VAE.**
On clean, plentiful data with simple laws, they tie (examples 01 and 06). The prior pays off with dirty or sparse data, for learning constants, and for laws the data rarely exercises.

**2. Tolerances can hurt.**
A law that is tighter than the decoder's reconstruction noise forces the model to trade fit for law-compliance. Normal data then scores worse and detection drops. Start loose. Tighten while watching held-out AUC.

**3. Posterior widths are optimistic.**
The battery example recovers Ea within a few percent, but its reported sd is far smaller than the true error. Mean-field variational inference and the decoder's approximation both shrink uncertainty. Treat posterior sd as a lower bound. Validate constants against a lab test.

**4. Latent dimension matters.**
Too few, and the manifold cannot fit (a closed loop needs 2 latent dims, example 00). Too many, and the decoder invents states in regions with no data; geodesics will cut through them (example 05). Use `path_support()` and aim near the system's true degrees of freedom.

**5. MW sees what is off the manifold — not what is subtle along it.**
An attacker or fault that moves the system to another *normal* state is invisible to a snapshot score. Use the Lorentzian cone for rates and direction over time; use domain constraints for known bad regions.

**6. Sensitivity has a floor.**
The validator in example 06 does not notice small solver errors (grid step ≤ 0.2). Scores average over all features, so one slightly wrong feature can hide in noise. For single critical laws, monitor the law residual directly as well.

**7. The training set defines "normal".**
Operating regimes absent from training (a new season, a new firmware) will raise false alarms. Retrain or add data. Calibration assumes the held-out normal data looks like future normal data.

**8. O(n) is about inference.**
Scoring one state costs one encoder and one decoder pass. Training still needs data, epochs and tuning. The comparison with PDE solvers is about *checking or emulating states*, not about solving the PDE to the same accuracy.

**9. Synthetic data.**
All examples use physics-generated data with known truth. Results on real systems will be lower and noisier. Treat the numbers here as a demonstration of mechanism, not as benchmarks.

**10. Not a safety system.**
This is research software. Do not use it as the sole protection for equipment or people.

===== FIXING_THE_GAPS.md =====
# Fixing the gaps — concrete next steps, not just a list of problems

This is the companion to `ROBOTICS.md`. That file reports what six robotics domains show
today; this one proposes specific, testable fixes for the three patterns that showed up
across them, in the order a researcher should probably try them. Every suggestion below
references code that already exists in this repo — none of it needs new infrastructure.

## Pattern 1: faults that are a *scaled* change to one channel score weakly

Across every domain, the fault that is a proportional multiplier on one reading —
`friction_increase` (joint, AUC 0.55), `link_bent` (arm, 0.67), `hotspot_short` (thermal,
0.57) — scores far below the faults that are a structural break (no_settle, overspeed,
bad_restitution: all 0.97–1.00). That is a consistent signature, not three unrelated weak
spots, and it points at one mechanism.

**Likely cause.** The anomaly's injected scale factor is sampled from a range (e.g.
`friction_increase` cuts `omega` by 30–55%) that can land inside the natural spread of
normal data, because normal data already varies a lot across `theta_ref`, `t`, position
along the beam, etc. A fault that is "30% off" is only detectable if 30% off is actually
rare in the training distribution at that particular combination of the other features.

**What to try, in order:**
1. **Positive control first, same principle used for the Rutooj sweep in `PYBAMM_ALTERNATIVE`.**
   Before changing anything, inject the *same* fault at 2–3x the magnitude (e.g. cut
   `omega` by 80% instead of 30–55%) and confirm the AUC rises toward 1.0. If it does, the
   current weak AUC is a real sensitivity limit at that fault size, not a bug — useful to
   know and report as such. If it does NOT rise, something else is wrong (see 3 below).
2. **Check `feature_attribution()` for these fault rows specifically**
   (`det.feature_attribution(df)` in `detector.py`, already built). If the top driver it
   names is NOT the channel the fault actually touched, the manifold is explaining the
   anomaly away through a different coordinate instead of flagging the right one — the
   same failure mode the Lorentzian tutorial's "split encoder" lesson warns about
   (`BATTERY_RIEMANNIAN_LORENTZIAN.py`'s header: a single encoder lets an anomaly signal
   hide in the wrong latent coordinate).
3. **Compare against a naive single-feature threshold** (e.g. z-score of `omega` alone, or
   of the single law residual most relevant to the fault). If the naive threshold beats the
   full MW distance, the extra flexibility of the manifold is absorbing exactly the signal
   that should trigger it — the fix is a tighter `law_tolerance` on that specific
   constraint, not a bigger model.
4. **Only after 1–3**, consider shrinking `latent_dim` for the affected domain (less room
   for the decoder to "explain away" a subtle anomaly) or tightening `obs_sigma` on the
   one most diagnostic feature.

## Pattern 2: the prior-sampled (generated) states satisfy their own law 10–30x looser than the training noise — in the pure-kinematic and impact domains only

`flexible_robot`, `joint_actuator` and `actuator_thermal` (all ODE/PDE domains, laws tied
to a differential equation) generate states whose law residual is within about 1x the
training sensor noise. `planar_arm`, `mobile_robot` and `legged_contact` (pure algebraic/
kinematic identities, or a ballistic+impact law) generate states 10–30x looser. Anomaly
detection still works well in two of those three (`legged_contact` 0.99+, `mobile_robot`
0.73–1.00); it is a separate finding from Pattern 1, about what the unconditional prior
produces, not about fault sensitivity.

**Likely cause, two candidates to test, not yet distinguished:**
- **Scale mismatch.** `planar_arm`'s `x,y` range over roughly ±1.8 and `legged_contact`'s
  `z,vz` range over a few units; a `law_tolerance` of 0.03 is a much smaller fraction of
  that range than it is of the beam's or joint's more tightly-scaled features. Check
  `obs_sigma` and the constraint tolerance against the actual per-feature standard
  deviation of the training data (`MWNormaliser` already computes this) before assuming the
  architecture is at fault.
- **Latent capacity in low-data regions.** `docs/LIMITATIONS.md` point 4 already documents
  this exact risk: "too many [latent dims], and the decoder invents states in regions with
  no data; geodesics will cut through them." `geometry.py::path_support()` exists
  specifically to check this — run it on these three domains before assuming it's a
  tolerance problem rather than a dimensionality one.

**What to try, in order:**
1. Run `path_support()` (already in `geometry.py`) on `PlanarArmVAE`, `MobileRobotVAE`,
   `HoppingContactVAE` to see whether generated points actually fall in sparsely-trained
   latent regions.
2. If so, reduce `latent_dim` for these three (currently 5, 5, 4) toward the system's true
   degrees of freedom (`planar_arm` has 4 independent inputs — `theta1, theta2, theta1dot,
   theta2dot` — everything else is derived; `legged_contact` has 2 — `t, v0` — plus `e`).
3. If not, recheck `obs_sigma` scaling per feature against each domain's actual data range,
   the same check `docs/LIMITATIONS.md` point 2 recommends ("start loose, tighten while
   watching held-out AUC").

## Pattern 3: the beam's coarse-simulator test moved the wrong way (already in ROBOTICS.md)

Documented there as: dropping a vibration mode removes energy, and the beam's current laws
don't penalise a trajectory that is too *smooth*, only one that is too energetic or
inconsistent. This one has a concrete, small fix already available in the codebase:

**`core.py::bound()` already accepts both `low` and `high`.** The beam's current C2 is
one-sided: `bound("c2_energy_envelope", excess - ceiling, high=0.0, ...)` only penalises
*exceeding* the decay envelope. Replacing it with a narrow two-sided band around the
expected decay curve —
`bound("c2_energy_envelope", excess, low=0.9*ceiling, high=1.1*ceiling, ...)` (tune the
0.9/1.1 width against held-out normal data first) — would also penalise a trajectory that
decays unnaturally fast, which is exactly what the coarse simulator with mode 2 dropped
does. This is a one-line change to test, not new infrastructure. Re-run
`examples/00_flexible_robot_validator.py`'s coarse-fidelity sweep after making it, and
check the direction flips the right way before declaring it fixed.

## How to tell a fix actually worked

Use the same standard already applied to the battery evidence in
`PYBAMM_ALTERNATIVE/EVIDENCE.md`, not a single improved number:
1. **Re-run with a different seed.** A single-seed AUC jump from 0.57 to 0.85 could be
   retraining noise; check it holds across at least 3 seeds before writing it up.
2. **Re-run the positive control alongside the real fix**, so a change that only works
   because the fault got easier (bigger injected magnitude) is distinguishable from a change
   that works because the model actually improved at the original magnitude.
3. **Report the faults that stay weak, not just the ones that improve.** The honest
   write-up style this repo already uses (see `ROBOTICS.md`) is the standard to hold a fix
   to as well — a partial improvement reported plainly is more useful to the next person
   than a single good number with the rest quietly dropped.

# MW Robotics — code companion

**Modak-Walawalkar (MW) Framework, trimmed to one domain: robotics.**

The MW Framework learns the physics of a system from data and Bayesian priors (Pyro SVI on a
physics-constrained Bayesian VAE — not plain PyTorch; the priors and the uncertainty they
carry are load-bearing, not a penalty term bolted on afterward), with no GPU cluster and no
PDE solver at inference time. It is validated and in production in one hard domain: battery
fleet analytics, where it holds up against open datasets (Sandia, HUST) and against an
independent researcher's own data. That is the proven core.

This repository takes that same core and points it at a new frontier: **robotics**. It now
spans **six genuinely different robotics physics systems** — a PDE, two ODEs, a pure
kinematic chain, a nonholonomic constraint, and a hybrid/impact dynamics problem — with
**zero changes to the underlying machinery**. Same `core.py`, same Pyro SVI training loop,
same `MWDetector` API, six times over. See [ROBOTICS.md](ROBOTICS.md) for the full result —
strong in parts, with a clear, written-down map of where the next iteration should focus
([FIXING_THE_GAPS.md](FIXING_THE_GAPS.md)), which is exactly what a first wave of experiments
on new ground should produce.

Two Zenodo preprints underlie the approach: the theory above (DOI 10.5281/zenodo.19304813),
and ["World Models with an Irreversible Time Axis"](https://doi.org/10.5281/zenodo.22954118)
(DOI 10.5281/zenodo.22954118), which frames MW as a fourth family of world models alongside
Dreamer, JEPA and generative video — battery evidence so far; see "Read next" below for what
it opens up for robotics.

**Two claims, kept separate so credit lands where it's earned:**
- **The core MW mechanism works, and that is the headline.** It is pushed on the strength of
  real evidence (battery: production use, open-dataset validation, an independent
  researcher's sweep) and it carried over unedited to six brand-new robotics physics systems
  — no small thing for a method with no GPU requirement.
- **Each robotics domain in this repo is a first exploration of new ground**, not a finished
  product: new laws, tested once each, strong on some faults and still being tuned on
  others. They're public exactly so other researchers can build on them faster than starting
  from scratch. See `ROBOTICS.md`'s "Status, in two tiers" and `FIXING_THE_GAPS.md`.

## The idea in four lines

1. Physics confines a real system to a thin surface — a **manifold** — inside its sensor space.
2. A Bayesian VAE **learns** that surface from normal data.
3. Known laws enter as **priors and likelihood terms**, so the learned surface must obey them.
4. Anything new is scored by its **MW distance** from the surface. One forward pass. O(n) in the number of features.

```
classical:  physics -> PDEs -> numerical solve (grid, time steps)     -> answer
MW:         physics -> Bayesian priors -> learned manifold -> one pass -> answer
```

## The six robotics domains in this repo

| # | Example | System | Physics | Laws |
|---|---|---|---|---|
| 00 | `flexible_robot.py` | Flexible-link arm / soft-robot segment | Euler-Bernoulli beam PDE | moment-curvature, energy-decay envelope, strain limit |
| 01 | `joint_actuator.py` | A single PD-controlled motor + link | damped 2nd-order ODE | Newton's-2nd-law torque/dynamics identity, energy envelope, torque limit |
| 02 | `planar_arm.py` | 2-link planar manipulator | pure kinematics (no ODE/PDE) | forward-kinematics identity, Jacobian (velocity) identity, joint limits |
| 03 | `mobile_robot.py` | Differential-drive mobile robot | nonholonomic kinematics ODE | no-sideways-motion constraint, heading-rate identity, speed limit |
| 04 | `legged_contact.py` | Hopping/legged robot foot, flight phase | ballistic motion + restitution (hybrid/impact) | energy conservation in flight, non-penetration, restitution bound |
| 05 | `actuator_thermal.py` | Motor winding / actuator housing | 1D heat-diffusion PDE | Fourier's-law identity, decay envelope, over-temperature limit |

Each one follows the same recipe: an exact closed-form dataset (no numerical solver), three
physics laws written as Bayesian priors, and three realistic injected faults. Run any of
them:

```bash
pip install -r requirements.txt
python examples/00_flexible_robot_validator.py      # or 01..05 - GPU auto-used if present
pytest -q
```

## What the six experiments show

Full tables and discussion in [ROBOTICS.md](ROBOTICS.md); the pattern across all six, stated
plainly:

- **The mechanism transfers every time, with zero framework changes** — a PDE, two
  different ODEs, pure kinematics, a nonholonomic constraint, and a hybrid/impact problem,
  all trained the same way, all scored the same way.
- **"Obviously wrong dynamics" faults are caught very well everywhere**: lost damping,
  cooling failure, overspeed, bad restitution, an impossible energy gain — all score
  ROC-AUC 0.97–1.00.
- **"Subtly scaled" faults are consistently weaker**: a partial friction increase, a bent
  link, a partial winding short — all score ROC-AUC 0.55–0.67. That's a real, repeated
  signature across unrelated domains, not noise, and [FIXING_THE_GAPS.md](FIXING_THE_GAPS.md)
  lays out exactly how to test and fix it.
- **One coarse-simulator test (the beam) came back backwards** — also diagnosed, with a
  concrete one-line fix proposed, in [FIXING_THE_GAPS.md](FIXING_THE_GAPS.md).

A working robotics validator or simulator isn't proven yet. What is proven is that the
mechanism carries over to six different kinds of robotics physics with zero framework
changes, and every experiment's result points at a specific, testable next step rather than
a dead end.

## Performance: no GPU required, measured

Inference (median of repeated `mw_distance` calls, after warm-up, on this machine's CPU —
i5-12450H — and RTX 3050 laptop GPU):

| Domain | CPU, 1 sample | GPU, 1 sample | CPU, batch of 1000 | GPU, batch of 1000 |
|---|---|---|---|---|
| flexible_beam | 1.14 ms | 3.43 ms | 107.4 ms (0.107 ms/sample) | 3.63 ms |
| joint_actuator | 1.30 ms | 2.57 ms | 50.3 ms (0.050 ms/sample) | 2.43 ms |
| planar_arm | 1.08 ms | 2.07 ms | 87.3 ms (0.087 ms/sample) | 2.04 ms |
| mobile_robot | 1.08 ms | 3.39 ms | 90.0 ms (0.090 ms/sample) | 3.47 ms |
| legged_contact | 1.28 ms | 2.08 ms | 70.1 ms (0.070 ms/sample) | 2.11 ms |
| actuator_thermal | 1.23 ms | 3.56 ms | 58.3 ms (0.058 ms/sample) | 3.53 ms |

**At single-sample inference — scoring one new sensor reading as it arrives, the realistic
deployment pattern — CPU is faster than GPU**, by about 2–3x: GPU kernel-launch overhead
dominates at batch size 1 and never gets amortised. GPU only pulls ahead at batch scale
(1000 at once: 15–30x faster), which matters for sweeps and fleet-wide scoring, not for
reading one state at a time.

Training (same model, `flexible_robot`, 200 epochs on 4000 rows, identical code path, only
`MW_DEVICE` changed):

| Device | Time | Per epoch |
|---|---|---|
| GPU (RTX 3050 laptop) | 105.6 s | 527.7 ms |
| CPU (i5-12450H) | 181.7 s | 908.4 ms |

CPU training is about 1.7x slower than GPU here — and still 3 minutes, start to finish, on a
laptop. Training is practical on CPU alone; it doesn't need a GPU, it's just faster with one.

===== ROBOTICS.md =====
# Robotics in MW_Robotics — status and limits (2026-10-31)

This folder is `MW_Framework` plus six new domains, each a genuinely different piece of
robotics physics: a PDE (a flexible-link beam), two different ODEs (a joint actuator, a
mobile robot's nonholonomic kinematics), a pure-kinematics chain (a planar arm), a
hybrid/impact problem (a legged robot's foot contact), and a second PDE (motor thermal
diffusion). Run any of `examples/00_flexible_robot_validator.py` through
`examples/05_actuator_thermal_validator.py`. See [FIXING_THE_GAPS.md](FIXING_THE_GAPS.md)
for concrete, testable next steps on every gap below.

## Status, in two tiers — read this before anything else

**Tier 1 — core MW mechanism: a proven result, and the reason this is worth building on.**
`core.py`'s machinery (priors as likelihood terms via Pyro SVI, a VAE on a physics-constrained
manifold, O(n) inference, MW distance as an anomaly score, calibration) is unchanged from the
parent `MW_Framework` repo, where it is validated on battery data: production deployment,
open Sandia/HUST held-out cells, and an independent researcher's own sweep (see
`PYBAMM_ALTERNATIVE/EVIDENCE.md` in the battery repo). That same mechanism, unedited, now also
runs correctly on six brand-new robotics physics systems it had never seen code for — a PDE,
two different ODEs, pure kinematics, a nonholonomic constraint, and a hybrid/impact problem.
No GPU cluster is needed at any point: inference is faster on CPU than GPU for single
readings (see "Performance" below), and even full training completes in 3 minutes on a
laptop CPU alone. That's the part of this repo backed by real evidence, and it's a genuinely
rare thing to have working at all, let alone six times over.

**Tier 2 — each robotics domain: a first experiment on new ground.** Every domain's three
physics laws and dataset are new, untested-by-anyone-else code. The mechanism runs in every
case; some faults are caught cleanly already, others only partly — exactly the kind of result
a first wave of experiments on brand-new domains should produce: strong enough to show the
approach is real, specific enough to show where to push next. They're public as a starting
point so other researchers can build on them, extend them, or improve the laws, rather than
starting from zero.

**The two claims to keep separate: "the MW mechanism generalizes to robotics" is supported by
six independent runs. "These six specific robotics validators are finished" is not — they're
version one.**

## Results across all six domains (measured 2026-10-31)

| Domain | False alarms (held-out normal) | Fault ROC-AUCs |
|---|---|---|
| flexible_robot (beam) | 1.6% | no_decay **1.00** · moment_glitch 0.64 · stiffness_loss 0.57 |
| joint_actuator | 0.4% | no_settle **0.97** · torque_sensor_glitch 0.91 · friction_increase 0.55 |
| planar_arm | 0.1% | encoder_drift 0.89 · velocity_glitch 0.89 · link_bent 0.67 |
| mobile_robot | 1.7% | overspeed **1.00** · wheel_slip 0.89 · gyro_glitch 0.73 |
| legged_contact | 0.7% | bad_restitution **1.00** · energy_gain **1.00** · ground_penetration 0.99 |
| actuator_thermal | 2.4% | cooling_failure **1.00** · flux_sensor_glitch 0.98 · hotspot_short 0.57 |

**Pattern 1 — faults that are a structural break are caught very well everywhere.** Lost
damping, a stuck/runaway joint, overspeed, bad restitution, an impossible mid-flight energy
gain, a cooling failure: every one of these scores 0.97–1.00, across five unrelated domains.
That's not a coincidence of one lucky run; it's the same mechanism catching the same *kind*
of fault — "this trajectory violates a hard physical identity" — every time it's tried.

**Pattern 2 — faults that are a subtle, scaled change to one channel are consistently
weaker.** `friction_increase` (0.55), `link_bent` (0.67), `hotspot_short` (0.57) all share
the same shape: a proportional perturbation that can overlap the normal range rather than
breaking an identity outright. This is a real, repeated signature across three unrelated
domains, not noise in one run — and [FIXING_THE_GAPS.md](FIXING_THE_GAPS.md) lays out the
specific, testable steps to find out why and fix it (starting with a positive control at a
larger fault magnitude, before changing any code).

**Pattern 3 — generated (prior-sampled) states satisfy their own law far more loosely in the
pure-kinematic and impact domains.** `planar_arm`, `mobile_robot` and `legged_contact`
generate states whose law residual is 10–30x the training sensor noise; the ODE/PDE domains
(`joint_actuator`, `actuator_thermal`, the beam) stay within about 1x. Anomaly detection
still works well in two of the three looser domains — this is a separate, specific finding
about what the unconditional prior produces, with concrete next steps in
[FIXING_THE_GAPS.md](FIXING_THE_GAPS.md).

## The beam's coarse-simulator test: one result that went the wrong way, diagnosed

Example 06 (Navier-Stokes, in the parent repo) showed MW distance rising as a coarse solver's
grid step grew. The equivalent test for the beam went the other way: distance fell as the
approximate simulator's fidelity dropped, and the flag rate stayed flat at the noise floor
across every fidelity level. Diagnosed, not left a mystery: dropping a vibration mode removes
energy, and the beam's current laws don't yet penalise a trajectory that is too smooth/quiet,
only one that is too energetic or inconsistent.
[FIXING_THE_GAPS.md](FIXING_THE_GAPS.md) proposes a concrete one-line fix, already supported
by existing code (`core.py::bound()` already accepts a two-sided band).

## Not yet a forecaster

All six domains are validators: they check whether a *given* state is physical. None of them
yet predicts the *next* state from the current one, the way a robot simulator (or the battery
SoH geodesic walk in the production battery product) does. Turning any of these into a
forward-time model that stands in for a robotics PDE/ODE solver is the natural next step —
see "Related theory" below for the architecture that points the way.

| mobile_robot | 1.08 ms | 3.39 ms | 90.0 ms | 3.47 ms |
| legged_contact | 1.28 ms | 2.08 ms | 70.1 ms | 2.11 ms |
| actuator_thermal | 1.23 ms | 3.56 ms | 58.3 ms | 3.53 ms |

At the realistic deployment pattern — one new reading at a time — CPU is 2–3x *faster* than
GPU, because GPU kernel-launch overhead dominates at batch size 1. GPU only wins at batch
scale (15–30x faster at 1000 at once), which matters for sweeps and fleet-wide scoring.

Training (`flexible_robot`, 200 epochs on 4000 rows, identical code, only `MW_DEVICE`
changed): GPU 105.6 s (527.7 ms/epoch) vs. CPU 181.7 s (908.4 ms/epoch) — about 1.7x slower
on CPU, and still 3 minutes end to end on a laptop. Training doesn't need a GPU; it's just
somewhat faster with one.

## Related theory: the architecture for closing the "not yet a forecaster" gap

Modak & Walawalkar, "World Models with an Irreversible Time Axis" (Zenodo, DOI
[10.5281/zenodo.22954118](https://doi.org/10.5281/zenodo.22954118), 2026) proposes exactly the
piece these six domains are missing: instead of a learned transition function, learn a
manifold of admissible states with a forward-only time axis, and *forecast* by walking the
manifold between the current state and a physics-projected target, rather than only checking
a single given state. It frames MW as a fourth family of world models, alongside latent
imagination (Dreamer), joint-embedding prediction (JEPA) and generative video (Genie/Cosmos)
— none of which can express "this state cannot be reached from that one."

What it's shown so far, and what's still ahead:
- **Proven in battery, not yet applied to robotics.** The paper's evidence is an EV fleet
  analytics deployment, plus an external validation against a published SEI-cracking study
  where the result was reproduced on the study author's own data and confirmed by them.
  Building the robotics version is the natural next step, not a result either repo has yet.
- **Even in the paper, the manifold isn't asked to do everything alone.** Its own Limitations
  section notes forecast *endpoints* still come from an external physics model; the manifold
  shapes the path between them. For any of these six domains, that means pairing the manifold
  with something that says where a trajectory ends up — a well-scoped, tractable next piece.
- **The Lorentzian cone (closest to this repo's anomaly work) has been tested on synthetic
  data and injected faults**, with real signal: normal transitions cluster inside the cone,
  injected fast-fade events cluster outside it, and the ~5% false-positive rate matches its
  95th-percentile calibration exactly as designed. Testing on recorded real fast-fade events
  is the next step there too.

Adapting this pattern to any of the six domains here — a forward-only time axis, a dedicated
clock encoder separate from the state encoder, and a target state fed in from the system's
own known dynamics — is the concrete next step toward a real forecaster, not just a
validator. `joint_actuator` and `legged_contact` are the most tractable starting points:
both already have an exact, known time-evolution law to supply the target state from.
